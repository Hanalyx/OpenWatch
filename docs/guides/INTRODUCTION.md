# Introduction to OpenWatch

OpenWatch is a continuous compliance platform for Linux fleets. It connects
to your servers over SSH, evaluates them with the [Kensa](https://github.com/Hanalyx/kensa)
rule corpus, and keeps the result as a timeline rather than a snapshot. It
answers what is passing now, what was passing on a given date, what drifted
since the last scan, and what needs attention before the next assessment.
Every finding carries the command that ran, its output, and the expected and
actual values, so the evidence is generated by the scan and not assembled
before an audit.

This document describes what OpenWatch does and how it is built. To install
it, read the [installation guide](INSTALLATION.md); to run a first scan, read
the [quickstart](QUICKSTART.md).

## The problem with point-in-time compliance

Most compliance tools scan a system and report what passes today. That is
necessary but not sufficient:

- **Posture decays at once.** A server that passed STIG on Monday can drift
  by Wednesday. Without continuous scanning, nobody knows until the next
  audit.
- **Historical questions go unanswered.** "Were we compliant during the
  assessment window?" needs a scan of the past, and a rescan only describes
  the present.
- **Exceptions live in spreadsheets.** Approved deviations sit in email
  threads and shared drives, disconnected from the finding they cover.
- **Drift is invisible.** When a passing rule starts failing, nobody notices
  until an assessor does.
- **Evidence is assembled, not generated.** Teams spend the days before an
  audit turning screenshots and command output into binders.

## What OpenWatch does

### Continuous posture on an adaptive schedule

The scheduler scans each host at an interval set by its compliance state, so
worse posture scans more often. The defaults run from every 4 hours for a
critical or never-scanned host to every 48 hours for a compliant one, and an
administrator can tune each band. The scan-cadence table in
[Scanning and compliance](SCANNING_AND_COMPLIANCE.md#adaptive-scheduling) is the
reference.

### Compliance over time

OpenWatch keeps a daily posture point per host and aggregates the fleet trend
from them. A day whose scan produced no score is reported as having no score,
not as zero: zero means every evaluated rule failed. The trend endpoints and
the dashboard read the same history.

### Drift detection

After every completed scan, OpenWatch compares the host's score with the
score before it. A drop raises a drift alert (major or minor by size) and a
large gain raises an improvement alert; the event is also written to the
audit log. Every rule whose status changed is recorded as a transaction, so
a regression traces to the rule and the scan that found it. Alerts move
through acknowledge, silence, resolve and dismiss. The packaged service
raises these alerts from its in-process worker; a separate `openwatch
worker` process records drift but does not alert (see the
[scaling guide](SCALING_GUIDE.md)).

### Exceptions with an audit trail

An exception names a rule, a reason and an expiry date. It moves through
request, approval or rejection, and revocation, and every transition is an
audit event. The exception register is one of the built-in report kinds.

### Remediation with a plan and a rollback

A remediation request shows its plan before anything runs, waits for approval,
and records each phase as it executes. Kensa applies fixes through 29 typed
mechanisms and keeps the pre-change state in a durable store so a fix can be
rolled back. [Hosts and remediation](HOSTS_AND_REMEDIATION.md) covers the
workflow.

### Evidence, reports and exports

Every check records the command, the raw output, the expected value and the
actual value. Reports come in four kinds (executive summary, framework
attestation, exception register, remediation activity) and export as PDF,
JSON, CSV or OSCAL SAR. Each report carries a content hash and an Ed25519
signature that an auditor can verify without OpenWatch; see
[Verifying a report](../runbooks/REPORT_VERIFICATION.md). The audit log
exports as CSV or JSON under its own permission, `audit:export`.

### One scan, many frameworks

Each Kensa rule carries its framework references, so one scan produces
results for every framework the corpus maps: CIS and STIG benchmarks for RHEL
8, 9 and 10 and Ubuntu 22.04 and 24.04, NIST 800-53, PCI DSS 4, and the SRG.
Filtering by framework happens at query time, and a framework lens resolves
per host (`stig` on a RHEL 9 host is `stig_rhel9`). The keys and per-key rule
counts for the pinned corpus are kept in
[Scanning and compliance](SCANNING_AND_COMPLIANCE.md#available-frameworks),
so there is one place to update them when the `kensa-rules` package changes.

## How it compares

OpenWatch manages the lifecycle of compliance across a fleet, not only the
scan.

| | OpenWatch | Manual processes | Point-in-time scanners |
|---|---|---|---|
| Multi-host scanning | Scheduled, over SSH, no agent | SSH into each server | Script it yourself |
| Dashboard and history | Built in, per host and per fleet | Spreadsheets | None |
| Posture on a past date | A query | Not possible | Not available |
| Drift detection | Alerts with a lifecycle | Manual discovery | Not available |
| Exception workflows | Request, approve, expire, revoke, audited | Spreadsheets and email | Not available |
| Framework coverage | CIS, STIG, NIST 800-53, PCI DSS 4 from one scan | Whatever you check | One benchmark profile per run |
| Remediation | 29 typed mechanisms with rollback | Commands by hand | Basic scripts |
| Evidence | Structured per check, signed reports | Screenshots | Varies by tool |

Kensa takes a different approach from SCAP-based tools. It separates rules
from their implementations, treats frameworks as metadata on each rule, and
detects host capabilities at runtime. An organization with a SCAP mandate can
keep a SCAP tool for assessment and use OpenWatch for remediation,
governance and continuous monitoring.

## Architecture

OpenWatch is one Go binary backed by PostgreSQL.

```
+-------------------------------------------------------------+
|  openwatch serve                                      :8443 |
|    REST API under /api/v1 (HTTPS, TLS 1.2 minimum)          |
|    embedded React 19 UI (go:embed)                          |
|    in-process worker: scans, discovery, drift, remediation  |
|    Kensa engine (Go, linked in)                             |
+-------------------------------------------------------------+
        |                                  |
        | SQL                              | SSH to each target
        v                                  v
+---------------------------+     +-----------------------------+
|  PostgreSQL               |     |  Your Linux servers         |
|  application data and     |     |  RHEL 8, 9, 10 and          |
|  job queue (SKIP LOCKED)  |     |  Ubuntu 22.04, 24.04        |
+---------------------------+     +-----------------------------+
```

The corpus carries rules for the RHEL family (RHEL, Rocky, Alma, Oracle) and
for Ubuntu. Other distributions can be inventoried but report no applicable
rules; [Linux distribution support](LINUX_DISTRIBUTION_SUPPORT.md) has the
matrix, and it separates where the server runs from what it can scan.

- **The binary** serves the API and the embedded single-page UI over HTTPS
  on port 8443. There is no separate web tier and no reverse proxy to run.
  Service lifecycle is systemd (`openwatch.service`); no container runtime
  is involved.
- **The worker** runs inside `serve` and drains the PostgreSQL job queue:
  scans, host discovery, drift evaluation and remediation. A dedicated
  `openwatch worker` process can take scan load off the server; the
  [scaling guide](SCALING_GUIDE.md) states what it does and does not do.
- **PostgreSQL** holds hosts, credentials, scans, findings, users,
  exceptions, alerts, reports and the audit log, and is also the job queue
  (`SELECT ... FOR UPDATE SKIP LOCKED`, so several workers never claim the
  same job). Schema changes ship inside the binary as migrations and are
  applied by `openwatch setup` on install and by the package on upgrade;
  see [Database migrations](../runbooks/DATABASE_MIGRATIONS.md).
- **Kensa** is linked into the binary. It connects to targets over SSH,
  evaluates rules, applies remediation and returns structured results. It
  keeps remediation pre-state in a durable SQLite store under the service's
  data directory so a fix can be rolled back after a restart; back it up
  with the database ([Backup and recovery](../runbooks/BACKUP_RECOVERY.md)).
- **Targets** need nothing installed. Scans run over SSH with credentials
  stored encrypted in OpenWatch.

The retired Python implementation, with its separate backend, Docker
Compose, Redis, Celery and MongoDB, is archived outside this repository. Any
document that describes those components describes a product that no longer
exists.

## Security

| Control | What ships |
|---|---|
| Passwords | Argon2id hashing |
| Browser sessions | HttpOnly cookies; the UI stores no token |
| Access tokens | RS256-signed JWTs from `/api/v1/auth/login`, for scripts |
| API tokens | Long-lived per-user tokens, stored only as a SHA-256 hash, revocable |
| Multi-factor | TOTP enrollment and verification at sign-in |
| Credentials at rest | AES-256-GCM, keyed from the service's secret key |
| Authorization | Five built-in roles (`viewer`, `auditor`, `ops_lead`, `security_admin`, `admin`), custom roles, and a registry of 67 permissions |
| Audit | Authentication, authorization, scan, remediation, exception and configuration events, exportable |
| Rate limiting | Auth endpoints limited to 20 requests per minute per IP |
| Transport | HTTPS only, TLS 1.2 minimum |
| FIPS 140-3 | A separate build (`make build-fips`) on the Go-native FIPS module; `openwatch --version` reports the state measured from the running binary |
| Targets | No agent; SSH only |

[Security hardening](SECURITY_HARDENING.md) covers TLS, FIPS, rate limits and
audit logging in depth. [User roles](USER_ROLES.md) covers the permission
model. Report a vulnerability as described in
[SECURITY.md](../../SECURITY.md).

## Automation

Everything the UI does is a call under `/api/v1`, and `api/openapi.yaml` is
the contract. The running server publishes the same document at
`/api/v1/openapi.yaml` and a browser at `/docs`. The
[API guide](API_GUIDE.md) covers authentication, tokens and the main
workflows for CI/CD and SIEM integration.

## Who OpenWatch is for

| You are | You use | Built-in role |
|---|---|---|
| A system administrator running a Linux fleet | Hosts, credentials, scans, alerts, executing approved fixes | `ops_lead` |
| A security engineer setting and enforcing baselines | Framework lenses, remediation approval, audit export | `security_admin` |
| A compliance officer or auditor | Trend, reports, exception approval, audit export | `auditor` |
| Anyone who needs to look and not touch | Read-only views | `viewer` |
| The platform administrator | Users, roles, SSO, settings, retention | `admin` |

A user may hold more than one role, and an administrator can create custom
roles. [User roles](USER_ROLES.md) lists every permission each role holds
and how a request is bound to one role.
